# Security design notes: feature expansion (signed off; as built)

Each feature below is on the secure coding standard's escalation list (SC-AGT-006). Each note lists what changes,
the controls that were planned, the decisions that needed a human answer (marked **Decide**) and, under **As built**,
what was implemented and where it differs from the plan. Last updated 2026-11-16.

## 1. Notifications and reminders

**What changes:** an in-app inbox (new `notifications` table, per user) and optional email digests over SMTP. This
adds a new outbound destination (the SMTP server).

**Controls planned**
- Inbox items are generated by a scheduled job from the same rules as "Needs attention" and "My tasks"; each user
  sees only their own items (`authorize()` plus a user-id filter; 403/404 tests for other users' items).
- Email: SMTP host, port and sender come from environment variables; the password comes only from an environment
  variable or a secret file, is never stored in the database, and is never logged (SC-SEC). TLS is required
  (STARTTLS or implicit TLS, certificate verified); a plain-text fallback is refused (SC-OUT).
- Emails contain titles and links to Keystone only, no record contents. Links are built with `public_link()`
  (`KEYSTONE_PUBLIC_URL`), never from the request's Host header.
- Each user opts in to a daily or weekly digest. Send failures are logged without addresses and retried with backoff.

**Decide:** (a) Is email in scope now, or only the in-app inbox for the first release? (b) Is a single SMTP relay
the only outbound host? (c) Default digest frequency: off, daily or weekly?

**As built:** in-app inbox and a daily email digest (on by default; each person can turn it off). Decided: email and
inbox, a custom SMTP relay, daily digests. Differences from the plan: the relay is configured in the app (Settings →
Email) rather than only by environment variables, so its password is stored Fernet-encrypted, write-only and bound to
the host it was entered for (changing the host drops it); only relays with public addresses are allowed unless the
operator lists an internal one in `KEYSTONE_SMTP_PRIVATE_HOSTS`; connections are pinned to the checked address with
TLS required. Later additions: attention items are routed to the owner of each record (docs/workflow-analysis.md),
@mentions and attack surface alerts arrive in the same inbox, and invitations, vendor links and Trust Center access
can be emailed.

## 2. Vendor self-service portal

**What changes:** a new external access path (vendors without accounts), plus file uploads from outside the company.

**Controls planned**
- A link per questionnaire: a 256-bit random token in the URL fragment (`#token=`), sent to the API in a header and
  stored only as a hash, as for invitations and Trust Center access. It expires (default 30 days), staff can revoke
  it, and it becomes read-only once submitted.
- The token grants access to that one questionnaire only: no internal IDs, no other vendors, no staff names.
- Public endpoints are rate-limited per token and per IP. Every view, save and submit is audited.
- Uploads go through the existing attachment guard: size cap, allowed extensions and content-type sniffing, stored
  outside the web root, served only to staff with `Content-Disposition: attachment`. Archives aren't extracted.
  There is no antivirus scanning (no scanner available); see Decide.
- Answers are shown to staff as text, never rendered as HTML.

**Decide:** (a) Allowed upload types and size (proposal: PDF, PNG, JPG, DOCX, XLSX; 10 MB each; 20 per
questionnaire). (b) Is shipping without antivirus scanning acceptable, or must a scanner (for example ClamAV) be a
precondition? (c) Default link lifetime.

**As built:** as proposed, with the decided file types and limits (PDF, PNG, JPG, DOCX, XLSX; 10 MB; 20 per
questionnaire), ClamAV scanning required and fail-closed (scanner down: uploads refused with 503; infected: refused and
audited), and links that never expire unless staff set a date (the organisation's decision; mitigated by revocation,
one active link per questionnaire, read-only after submission, rate limits and audited actions).

## 3. Auditor workspace

**What changes:** time-limited access for external auditors and an export (ZIP) of evidence.

**Controls planned**
- Auditors get a normal Keystone account with the existing read-only `auditor` role, plus an expiry date on the
  account (new `expires_at` on users; sessions end at expiry). No new anonymous link type.
- A PBC (evidence request) list: staff create requests, auditors comment, staff attach evidence. Comments are text
  only, length-bounded and audited.
- The audit pack ZIP (SoA, approved policies, current evidence per control) is generated on request from stored
  files only. Archive entry names are built by Keystone (slugged), never taken from user input, which prevents path
  traversal (zip-slip). The total size is capped and the export is audited.

**Decide:** (a) Is account expiry acceptable, or do you want auditor access without accounts (a token link)? This
changes the role and permission model. (b) May auditors download evidence files, or only view the list?
(c) Size cap for the audit pack (proposal: 500 MB).

**As built:** auditors get normal accounts with the Auditor role and a required expiry date; sign-in and existing
sessions stop at expiry. They can view (in-app viewer for PDF, images and text; files are still served as downloads)
and download evidence. Evidence request list with comments; audit pack ZIP capped at 500 MB with generated entry names
and a SHA-256 manifest. Also fixed while building it: changing a user's role now ends their sessions.

## 4. Single sign-on (OIDC: Entra ID, Google, Okta)

**What changes:** authentication. This adds new outbound destinations (each identity provider's discovery and token
endpoints).

**Controls planned**
- Authorization code flow with PKCE (S256), `state` and `nonce` bound to a short-lived server-side login record.
  The ID token's signature is checked against the provider's JWKS with pinned algorithms (RS256/ES256, never
  `none` or HS*), and `iss`, `aud`, `exp`, `iat` and `nonce` are verified. Discovery is fetched only from an
  admin-configured issuer over HTTPS.
- The client secret is stored encrypted (Fernet, as for integrations) and is write-only in the API.
- Users are matched by the provider's subject (`sub`) plus issuer, not by email alone. Just-in-time creation is off
  by default; an admin links or pre-creates users. SSO users get the same sessions, CSRF protection and timeouts.
- Optional "SSO required" setting: password login is disabled for everyone except one break-glass admin.
- Tested against a fake identity provider in the test suite (no live tenant).
- Outbound requests: HTTPS only, timeouts, no redirects followed, and the issuer host is pinned the same way as the
  website integration (resolved once, public addresses only).

**Decide:** (a) Which providers to support first? (b) Just-in-time user creation (with a default role of
`viewer`), or admin-linked only? (c) Should "SSO required" exist, and who is the break-glass account?
(d) Does a new authentication library need approval (for example Authlib), or should the OIDC client be written on
`httpx` plus a JWT library? Either way it is a new dependency for SC-DEP-002 review.

**As built:** Entra ID and Google (Okta not built). Accounts: an administrator creates the user and the first SSO
sign-in links it by email (Entra single-tenant only; Google verified emails only), after which only the provider's
issuer and subject are used; optionally, approved domains create accounts automatically with the Employee or Viewer
role. Authlib 1.9.5 with joserfc 1.8.0 (SC-DEP-002 checks recorded in the commit). Provider endpoints are fixed in code;
no discovery URL comes from configuration. "SSO required" was decided later: every administrator (not one named
account) keeps password sign-in as the break-glass route; it can only be turned on while a provider is on.

## 5. Attack surface management

**What changes:** read-only connectors to customers' RMM, EDR, vulnerability management and Microsoft 365 tenants (new
outbound destinations, including self-hosted servers), a device and identity inventory, baselines and findings.

**Decided (human:sneh, 2026-11-16):** NinjaOne, Datto RMM, N-central, ConnectWise Automate; Microsoft Defender,
CrowdStrike, SentinelOne, Sophos; Tenable, Qualys, Rapid7, Defender Vulnerability Management; and Keystone may call
Microsoft APIs directly, read-only (the Entra exposure module keeps using the collector).

**As built:**
- One HTTP client for every connector (`keystone/integrations/http.py`): HTTPS only; each connector's exact hosts or its
  vendor's domain for customer consoles; pagination links re-checked; self-hosted servers public-only unless listed in
  `KEYSTONE_INTEGRATION_PRIVATE_HOSTS`; connections pinned to the checked address; no redirects; size, page and time
  limits; errors never repeat response bodies.
- Credentials encrypted and write-only; for self-hosted servers they are dropped when the server address changes.
- Untrusted XML (Qualys) parsed with defusedxml.
- Exceptions to baselines need risk-acceptance rights, a reason and an end date within a year, and can't be approved
  for your own device or account.
- Connectors were built from vendor documentation and tested with sample responses, not live tenants; each records how
  its field mapping was verified, and Test connection lists the field names a real API returns.

## 6. Smaller decisions

| Decision | Detail |
|---|---|
| Comments | Any staff member who can read a record may comment (existing `read` permission); employees can't |
| File downloads by number | Checked against the record a file belongs to; device screenshots, removed vendor files and unlinked files are never served through it |
| Backups and restore (round 3) | Nightly, test-restored, owner-only file permissions; the encryption key is excluded. Restore is a server command into an empty database, reads only allowlisted archive member names, verifies every checksum before writing, and writes attachments only under their own verified hash. No web upload or restore of backups |
| Health endpoint | `GET /api/health` is public and returns only `ok` or 503 (database unreachable). Job and backup details need `users.manage` (`GET /api/system/health`); errors are shown by exception type only |
| PostgreSQL password | Read from `KEYSTONE_DB_PASSWORD_FILE` (a Docker secret), so it isn't in the environment or compose file |
| Vulnerability feeds (round 3) | Two new outbound destinations, both public and unauthenticated: `www.cisa.gov` (KEV JSON) and `epss.empiricalsecurity.com` (EPSS daily CSV). Exact-host policy through the shared client; whole files only, so nothing about the organisation is sent; 50 MB download and 200 MB decompression caps; each feed can be turned off |
| External attack surface (round 3) | Enumerates and probes only domains verified by a Keystone-generated DNS TXT record, re-checked before each scan; hosts must be the domain or its sub-domains. New outbound destinations: `crt.sh` (exact host, through the shared client) and the domains' own public hosts on 443/80 via the website check (public addresses only, pinned). DNS through the server's resolver. No port scanning. The verification token is shown only to users who can manage integrations |
| Cloud posture sources (round 3) | AWS Security Hub (boto3; region validated so the endpoint host can't be steered), Microsoft Defender for Cloud (`login.microsoftonline.com`, `management.azure.com`; Security Reader role, no Graph permissions), Google Security Command Center (`oauth2.googleapis.com`, `securitycenter.googleapis.com`; Findings Viewer). All read-only; keys encrypted and write-only. The Google token endpoint is fixed: a `token_uri` in the uploaded key file is ignored. Pagination links are checked against each connector's host policy |
| Ticketing (round 3) | Write connectors, create-only: Jira (`*.atlassian.net`), ServiceNow (`*.service-now.com`), ConnectWise PSA (cloud API hosts or a self-hosted server with a public address / operator allowlist), Autotask (`*.autotask.net`). Credentials bound to the site (dropped on change). Ticket content built server-side; incidents send reference, title and severity only. Raising a ticket needs the record's write permission; one ticket per record per system; automatic tickets capped at 25 per run and off by default |
| Privacy and continuity (round 3) | New permissions `privacy.write` (admin, ISMS manager) and `continuity.write` (also risk owners); no existing role lost anything. Data subject requests are need-to-know (`privacy.write` to read), their requester fields are redacted in the audit log and cleared after `KEYSTONE_DSR_REDACT_DAYS`. DPIA decisions need `risk.accept` and a different person from the author |
